## 1. 한눈에

1. **되돌리기가 가장 약하다.** `brain undo`와 앱 설정의 [되돌리기]는 "그 자리의 파일이 그 작업이 남긴 그대로인지" 보지 않고 경로만 보고 덮거나 치운다. 그래서 버린 초안을 되살리면 **그 자리에 새로 저장한 노트가 흔적 없이 사라지고**(휴지통·사본에도 없음), 제목을 바꾼 노트의 앞 고침을 되돌리면 같은 번호의 노트가 둘이 된다. 8가지 순서를 모두 재현했다.
2. **잠금 밖에서 고치는 파일이 남아 있다.** 할 일 추천 3개를 한꺼번에 부르면 사본에서 20번 중 20번 일부가 사라졌다(60개 중 25개만 남음, "넣음"이라고 답하고). 실수 노트 횟수·세션 읽은 범위도 같은 모양이다. 색인을 동시에 맞추면 한쪽이 오류로 죽는데, 저장을 마친 `brain add`가 죽으면 "저장됐는데 실패로 보이는" 경우가 된다(실제 폴더 사본에서는 300번 중 0번, 노트가 거의 없는 작은 폴더에서는 5번 돌려 5번 모두 4개 중 하나가 죽음).
3. **노트 저장·옮기기·색인 자체는 튼튼했다.** 동시에 저장 400번에 번호 겹침 0, 저장 도중 강제 종료 40번에 반쪽 파일 0, 5,000개를 옮기다 죽여도 5,000개 그대로, 색인 버전이 바뀐 직후에도 정상이었다. 실제 지식 폴더에는 지금 이 버그들의 흔적(겹친 번호·남은 임시 파일)이 없다.

### 3.1 버그 (재현 시험 있음)

| # | A 다음에 B | 일어나는 일 | 크기 |
|---|---|---|---|
| 1 | 초안을 버림 → 같은 주제에 같은 제목으로 다시 저장 → "버림"을 되돌림 | 새 노트가 버린 초안의 옛 내용으로 **덮여 사라진다**. 휴지통에도 되돌리기 사본에도 없다 | 높음 |
| 2 | 세션 ㄱ이 노트 저장 → 버림 → 세션 ㄴ이 같은 자리에 저장 → 세션 ㄱ 묶음을 되돌림 | 세션 ㄴ의 노트가 휴지통으로 간다 | 높음 |
| 3 | 노트를 고침 → 제목을 바꿈(파일 이름이 바뀜) → 앞의 고침을 되돌림 | 같은 번호의 노트가 **두 파일**. 옛 내용이 다른 번호(`f_…`)로 AI 찾기에 다시 나온다 | 높음 |
| 4 | 제목을 바꿈 → 고침 → 제목 바꾸기를 되돌림 | 뒤의 고침이 휴지통으로 가고 옛 내용만 남는다. 이어서 뒤 고침을 되돌리면 두 파일 | 높음 |
| 5 | 노트를 고침 → 버림 → 앞의 고침을 되돌림 | 버린 노트가 고치기 전 내용으로 되살아난다 | 중간 |
| 6 | 같은 노트를 두 번 고침 → 앞 고침을 되돌림 | 뒤 고침이 사본 없이 사라진다 (**전부터 적혀 있던 약점**, 기능검토 1-5 — 아직 열려 있다) | 중간 |
| 7 | AI가 할 일을 추천 → 사용자가 할 일을 적음 → 추천을 되돌림 | 할 일 파일이 통째로 추천 전 상태가 된다(사용자가 적은 것까지) | 중간 |
| 8 | 새 노트 → 제목을 바꿈 → 새 노트를 만든 작업을 되돌림 | 아무것도 되돌리지 않고 "되돌림"으로 적는다(다시 되돌릴 수 없음) | 낮음 |
| 9 | 할 일 추천 여러 개를 한꺼번에 부름 (AI가 한 메시지에서 도구 3개) | "넣음"이라고 답한 추천이 사라진다 | 중간 |
| 10 | 실수 노트 "지킴" 횟수를 동시에 올림 | 횟수가 덜 세진다 (90번 → 85) | 낮음 |
| 11 | 세션 축약본을 두 곳에서 동시에 읽음 | 읽은 범위 기록이 사라져 "안 읽은 곳"이 틀린다 | 낮음 |
| 12 | 저장하는 동안 다른 명령(찾기·요청 훅·다른 저장)이 색인을 맞춤 | 한쪽이 오류로 죽는다. 저장을 마친 `brain add`·앱 저장이 죽으면 **저장됐는데 실패로 보인다** → 다시 저장해 중복 초안. 훅이 죽으면 그 요청에 규칙·노트가 조용히 안 붙는다 | 중간(드묾) |
| 13 | 색인 파일이 아직 없는 새 지식 폴더에서 첫 명령 여러 개를 한꺼번에 | 4개 중 3개가 "database is locked"로 실패 (아무것도 쓰기 전이라 손실 없음) | 낮음 |

### 3.3 확인 못 함

| # | 무엇 | 왜 |
|---|---|---|
| 1 | 전원이 꺼져 변경 기록·되돌리기 목록의 한 줄이 반쯤 쓰임 | 프로세스를 죽이는 것으로는 못 만든다. 반쪽 줄을 읽는 곳 가운데 예외를 안 잡는 곳이 있다(되돌리기) |
| 2 | 제목 바꾸기 도중(새 파일을 쓰고 옛 파일을 지우기 전) 끊김 | 틈이 매우 짧아 재현하지 못했다. 끊기면 같은 번호가 두 파일이 된다 |
| 3 | 강제 종료가 남긴 잠금 표시(`_meta/.lock-<pid>`)를 같은 pid의 새 프로세스가 만남 | 표시가 남는 것은 확인(강제 종료 뒤 1~2개). 같은 pid를 받아야 10분 기다림이 생긴다 |
| 4 | 실제 앱 화면에서의 동시 동작(편집 창을 연 채 AI가 고침, 폴더 정리 중 저장) | 코드와 코어 시험으로만 봤다. 앱을 띄워 눌러 보지 않았다 |
| 5 | 목차를 "붙였다"고 적은 뒤 훅 글이 AI에게 못 감 | 받는 쪽을 닫아 흉내 내면 표시만 남고 다음 요청에는 "앞쪽에 있다" 한 줄만 간다. 실제 Claude Code에서 그런 끊김이 나는지는 못 봤다. 노트는 안전하다 |
| 6 | 달이 바뀌는 순간 변경 기록 첫 줄, 백업 zip을 만들다 끊김 | 코드로만 봤다(반쪽 zip이 정상 이름으로 남을 수 있음, 마지막 백업 시각은 안 바뀜) |
| 7 | 되돌리기 도중 다른 쓰기가 끼어듦 | 되돌리기는 지식 폴더 잠금을 잡지 않는다. 동시에 일어나게 만들지 못했다 |

## 4. 버그 자세히

### 4.1 되돌리기가 경로만 본다 (버그 1~8)

- **예**: AI가 "USB 디스크 시험 시간 초과" 초안을 틀리게 저장했다. 사용자가 정리 보드에서 [버림]. AI가 같은 제목으로 맞게 다시 저장했다(같은 주제라 같은 파일 자리). 며칠 뒤 사용자가 설정에서 그 "버림"을 [되돌리기] → 맞게 저장한 노트가 틀린 초안으로 바뀌어 있고, 맞는 내용은 어디에도 없다.
- **사본 재현 (실제 `brain`)**: 위 순서 그대로 — 되돌린 뒤 새 내용이 든 파일은 노트 폴더 0개·휴지통 0개·되돌리기 사본 0개, 새 노트 번호를 열면 "노트가 없습니다". 버그 3은 실제 노트 하나로: 고침 → `brain write --title` → `brain undo <앞 묶음>` 뒤 같은 번호가 두 파일이고 `brain find`에 옛 내용이 `f_…` 번호로 나왔다.
- **원인**: `undoBatch`(`packages/brain_core/lib/src/log/change_log.dart`)는 묶음에 적힌 경로에 사본을 덮어쓰거나, 그 경로의 파일을 휴지통으로 보낸다. 그 파일이 지금도 그 묶음이 남긴 것인지는 보지 않는다. 11/13에 "바꾼 뒤" 해시(`after.jsonl`)와 견주는 검사(`driftSinceBatches`)를 만들었지만 정리 보드의 [되돌리기]에만 넣었다. `brain undo`와 설정 [되돌리기]는 `undoBatch`를 바로 부른다. 옮기기만 따로 막았고(경로 바뀜 표시), 제목 바꾸기·버리기·같은 자리 새 노트는 빠졌다.
- **고칠 방향 (탐침으로 확인)**: 그 검사를 `undoBatch` 맨 앞에 둔다. 탐침에서 버그 1~8의 여덟 묶음을 모두 걸러 냈고, 정상 순서(가장 최근 묶음부터) 네 가지는 통과시켰다. 정할 것 두 가지:
  1. "바꾼 뒤" 기록이 없는 옛 묶음 — 실제 지식 폴더의 묶음 214개 가운데 138개(11/13 전) — 은 확인할 수 없다. 기본은 거절하고 `--force`를 둔다.
  2. `--force`로 덮을 때는 덮기 전 파일을 휴지통에 먼저 남긴다(무엇을 해도 내용이 사라지지 않게).

### 4.2 잠금 밖에서 읽고 고쳐 쓰는 파일 (버그 9~11, 20)

- **예**: AI가 노트를 저장하니 `brain add`가 상태 문장 3개를 알리며 "할 일이면 `brain todo suggest`로" 하라고 한다(11/14에 넣은 알림). AI가 한 메시지에서 `brain todo suggest` 3개를 같이 부른다 → 셋 다 "추천 칸에 넣음"이라고 답하지만 `todos.md`에는 1~2개만 있다.
- **사본 재현**: 3개씩 20번 → 20번 모두 일부가 사라졌고 60개 중 25개만 남았다. 하나씩 차례로 15개 → 15개. 코어 시험(일꾼 6개 × 15번)에서는 할 일 90개 중 59~61개 유실, 실수 노트 지킴 90 → 85.
- **원인**: 노트 저장(`add`·`write`·`update`·옮기기·합치기)은 지식 폴더 잠금 안에서 읽고 쓴다. 할 일(`TodoStore`의 모든 쓰기), 실수 노트의 고치기(`save`·`setStatus`·`recordEvidence`·시험 지우기·검사 기준 추가 — 새로 만들기와 합치기만 잠금 안), 세션 읽은 범위(`SessionReads.record`)는 잠금 없이 "읽기 → 고치기 → 쓰기"다. 원자적 쓰기의 임시 파일 이름이 시각(마이크로초)뿐이라 같은 순간에 쓰면 이름도 겹친다.
- **고칠 방향**: 이 쓰기들을 `withVaultLock` 안으로 옮긴다(읽기부터). 임시 파일 이름에 프로세스 번호를 더한다. 작은 고침이다.

### 4.3 색인을 동시에 맞추면 한쪽이 죽는다 (버그 12, 13)

- **일어나는 일**: 색인 맞추기(`SearchIndex.sync`)가 "지금 색인에 있는 줄 목록"을 쓰기 잠금을 잡기 **전에** 읽는다. 그 사이 다른 프로세스가 같은 새 파일을 색인에 넣으면, 낡은 목록을 든 쪽이 그 파일을 또 넣으려다 `UNIQUE constraint failed: docs.path`로 죽는다.
- **왜 문제인가**: 죽는 쪽이 방금 노트를 저장한 `brain add`(저장 뒤 색인 맞추기)면 노트는 저장됐는데 명령은 오류로 끝난다. AI는 실패로 알고 다시 저장한다 → 같은 초안이 둘. 요청 훅이면 오류를 삼키고 빈손으로 끝나 그 요청에 규칙·노트가 안 붙는다.
- **얼마나 자주**: 코어 시험(저장 둘 + 색인 맞추기 둘을 계속 돌림)에서 저장 80번 중 16~29번, 모두 노트가 저장된 뒤였다. 실제 `brain`으로는 노트가 거의 없는 폴더에서 4개 동시 저장 5번 중 5번 하나가 죽었고(그중 일부는 저장 뒤), **실제 지식 폴더 사본에서는 3개 동시 300번·찾기와 훅을 섞은 40번 모두 0번**, 노트 5,000개 폴더 30번도 0번이었다. 지금 크기에서는 드물다.
- **고칠 방향**: 줄 목록을 쓰기 잠금을 잡은 뒤에 읽는다(두 줄의 순서를 바꾸는 고침). 덧붙여 저장 뒤의 색인·목차 실패는 "저장함 + 색인은 다음에 맞춤"으로 알린다(저장 성공을 실패로 보이지 않게).
- **버그 13**은 색인 파일을 처음 만드는 순간의 경쟁이다(`pragma journal_mode = wal`에서 기다리지 않고 실패). 쓰기 전이라 손실은 없지만 새 사용자가 처음에 만날 수 있다.

### 4.4 AI가 적용 중인 규칙을 끌 수 있다 (버그 14, 정책 결정)

- **사본 재현**: AI 대화 환경에서 `brain lesson set L-0002 --status archived` → "L-0002 → 보관", 종료 코드 0. 세션 시작 안내에서 그 규칙이 빠졌다. 승인 대기로 내리기도 된다. 되살리기(`--status active`)는 사용자 말 근거(`--quote`)가 없어 거절된다 — 즉 AI는 끌 수는 있고 켤 수는 없다.
- **왜 지금**: 11/14 놓친 교정 줍기 실측에서 싼 모델이 `brain lesson set`으로 규칙을 보관해 그 실행의 허용 명령에서는 뺐다. 평소 대화에서는 그대로 열려 있다. 정리 보드의 "AI가 고친 노트"는 노트만 보여 주고 실수 노트는 안 보여 준다.
- **선택지**: (가) AI 대화에서는 적용 중 규칙의 보관·내리기를 거절하고 "사용자가 앱 [배운 것]에서" 안내 — 작다. (나) 허용하되 정리 보드에 "AI가 끈 규칙" 카드와 [되살리기] — 중간. 권장은 (가): 규칙을 끄는 일은 사용자가 정한다는 원칙(설계서_프롬프트이후 TL;DR 1)과 맞고, 승인 대기 규칙의 정리는 지금처럼 둘 수 있다.

### 4.5 11/14 경로의 작은 것 (버그 15~19)

- **놓친 교정 `--done`**: 받은 수를 그 세션의 실제 문장 수로 자르고, 표시 파일의 숫자가 아닌 값은 무시한다. 요청 전 훅의 읽기 명령 판정에서 `--done`을 쓰기로 본다(`sessions mark`와 같은 자리).
- **사진 붙인 초안 합치기**: 합칠 때 사진 링크를 대상 노트 자리 기준으로 다시 쓴다(옮기기에서 쓰는 함수가 이미 있다).
- **합쳐진 노트의 대상이 사라짐**: 점검에 "합쳐짐인데 가리키는 노트가 없음"을 더한다.

## 8. 재사용 점검표 — 이미 있는 기능들이 맞물릴 때 데이터를 잃는지 감사하기

프로젝트 이름 없이 따라 할 수 있게 적는다.

**판단 기준**

1. "예전 상태를 다시 쓰는" 기능(되돌리기·복원·옮기기 취소)은 **경로가 아니라 내용**으로 대상을 확인해야 한다. 경로만 믿으면 그 자리에 온 다른 파일을 덮거나 치운다. 덮기 전에는 지금 것을 어딘가에 남긴다.
2. 한 입구에 넣은 안전 검사는 **같은 일을 하는 다른 입구**(명령줄·설정 화면·자동 작업)에도 있는지 본다. 가장 최근에 고친 곳 옆이 비어 있기 쉽다.
3. 읽고 → 고치고 → 쓰는 파일은 **전부** 같은 잠금 안이어야 한다. "새로 만들기"만 잠그고 "고치기"를 빼먹는다. 여럿이 한 파일을 고치는 것(목록·횟수·상태 파일)부터 본다.
4. **잠금을 잡기 전에 읽은 값을 잠금 안에서 쓰지 않는다.** 잠근 뒤 다시 읽는다.
5. **성공했는데 실패로 보이는 길**을 찾는다. 다시 시도가 중복을 만든다. 본 작업 뒤의 부가 작업(색인·요약·알림)이 실패해도 본 작업은 성공으로 알린다.
6. AI가 부를 수 있는 명령은 "켜기"만큼 **"끄기·내리기·지우기"**도 지킨다.
7. AI가 옮겨 적는 숫자·번호는 틀릴 수 있다. 받는 쪽이 상한과 형식을 본다.

**확인 순서**

1. 이미 알려진 약점 문서를 먼저 읽는다(다시 보고하지 않게, 그리고 "알려졌지만 안 고친 것"을 구분하게).
2. 쓰는 함수 전부를 표로 만든다: 무엇을 읽나 / 무엇을 쓰나 / 잠금 안인가 / 되돌릴 기록을 남기나 / 실패하면 어디까지 쓰였나.
3. 동작(만들기·고치기·이름 바꾸기·옮기기·지우기·합치기·상태 바꾸기·밖에서 고치기) × 뒤따르는 일(앞 작업 되돌리기·뒤 작업 되돌리기·동시 실행·중간 끊김·파생 데이터 다시 만들기)로 짝을 만든다.
4. 짝마다 지켜야 할 것을 한 문장으로: 내용이 저장소 어딘가에 남는다 / 같은 번호는 파일 하나 / 성공이라 했으면 실제로 됐다.
5. 시험은 **안전한 결과**를 기대하게 쓴다. 고치는 방법(거절·합치기)을 정하지 않는다. 지금 깨지면 재현이다.
6. 임시 폴더 시험 다음에 **실제 데이터의 사본 + 실제 실행 파일**로 한 번 더 한다. 색인·캐시·기록 위치까지 따로 둔다.
7. 동시성은 둘로 잰다: 원리를 보이는 세게 돌리기(일꾼 여럿 × 수십 번)와, 실제 쓰는 모양(한 메시지에서 도구 3개)의 빈도.
8. 끊김은 예외를 던지는 것으로 끝내지 말고 **프로세스를 실제로 죽인다**(시점을 바꿔 수십 번). 죽은 뒤 셀 것: 파일 수, 겹친 번호, 반쪽 파일, 남은 임시·잠금 파일, 다음 명령이 도는지.
9. 고칠 방향을 내기 전에, 이미 있는 검사가 새 사례를 걸러 내는지 탐침으로 본다(되는 순서를 막지 않는지도).
10. 끝에 실제 데이터에 흔적이 있는지(겹친 번호·남은 파일) 읽기 전용으로 센다.

**빼면 안 되는 것 (이번에 실제로 틀렸거나 놓칠 뻔한 것)**

- "안전 확인"으로 쓴 시험이 깨졌을 때 시험 탓으로 넘기지 않는다. 이번에 색인 동시 맞추기 문제가 거기서 나왔다.
- 통과한 시험도 **왜 통과했는지** 본다. 시험 환경변수를 빈 문자열로 넣었더니 명령이 다른 까닭으로 실패해 "규칙이 안 꺼졌다 = 통과"로 보였다.
- 출력에서 번호를 뽑을 때 첫 번호를 집으면 안내 문장 속 다른 번호를 집는다. 결과 줄에서만 뽑는다.
- 세게 돌려야만 나는 문제를 "자주 난다"고 쓰지 않는다. 실제 사본에서의 횟수(300번 중 0번)를 같이 적는다.
- 스트레스 시험의 일꾼이 낸 오류를 삼키지 않는다. 오류 수와 유실 수를 따로 센다(임시 파일 이름 겹침을 그렇게 찾았다).
- 같은 캐시 폴더에서 다른 세션이 시험을 돌리고 있을 수 있다. 내가 만든 것이 아닌 폴더는 지우지 않는다.
- 사본을 만든 뒤 원본이 그대로인지, 실제 캐시·기록 폴더에 내 흔적이 없는지 끝에 확인한다.

**이번 숫자**: 시나리오 41개 가운데 버그 20(재현 시험 22개) · 안전 14 · 확인 못 함 7. 가장 큰 것은 "되돌리기가 경로만 본다" 하나의 원인에서 8가지가 나왔고, 이미 있던 검사를 한 곳 더 부르면 8가지가 모두 걸러진다.
