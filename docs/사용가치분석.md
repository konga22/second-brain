# 세컨드 브레인 사용 가치 분석: 쓰는 사람 vs 안 쓰는 사람 (2026-11-08)

- **질문**: 세컨드 브레인을 쓰는 사람과 안 쓰는 사람은 무엇이 다른가. 토큰을 얼마나 아끼고, 정보를 얼마나 얻고, 실수를 얼마나 덜 하나 (사용자 요청 11/08)
- **방법**: 실제 Claude Code(`claude -p`)에 같은 요청을 조건 4개로 2번씩, 모두 216번 보냈다. 찾은 약점을 고친 뒤(설계서 v1.3.16) 세컨드 브레인 조건만 54번 다시 쟀다. 응답의 `usage`(토큰)·턴 수·걸린 시간·답을 모았다(실측). 실제 지식 폴더(노트 50개·실수 노트 7개)의 사본을 썼다.
- **도구**: 준비 `bench/value/setup.sh`, 실측 `bench/value/run.py`, 요약 `bench/value/summary.py`. 측정 비용 합계 약 $1.3(Haiku)

## TL;DR

> **지난 결정을 물으면** 세컨드 브레인 없이는 24번 중 **2번만** 답했다(8%). 세컨드 브레인은 **24번 모두** 답했다(고친 뒤, 고치기 전 23번). 모르는 AI가 오히려 디스크를 뒤져 토큰을 더 썼다(질문당 8.7만 vs 4.2만). **답 하나를 얻는 데 드는 토큰은 105만 vs 4.2만, 25배 차이**다.
> 노트를 전부 `CLAUDE.md`에 넣어도 답은 나온다. 하지만 관계없는 요청까지 **매번 +4만 토큰(+151%)**이 들고, 노트 약 1,500개면 문맥이 찬다. 세컨드 브레인은 관계없는 요청에 **+6%**(실수 노트 목록 포함)만 들고, 노트 1만 개에서도 그대로다.
> **같은 실수**: 처음에는 사용자가 규칙과 다른 말로 요청하면 실수 노트가 안 붙어 6/12였다. 실수 노트를 세션 시작에 늘 보이게 고친 뒤 **11/12**다(안 쓰면 4.5/12, 통째로 넣기 10.5/12). 고친 내용은 8절에 있다.

## 1. 비교 조건: 세컨드 브레인이 없으면 사람들은 어떻게 하나

세컨드 브레인을 안 쓰는 사람이 실제로 고를 수 있는 방법 3가지를 조건으로 만들었다. 노트 내용은 네 조건 모두 같다.

| 조건 | 무엇을 흉내 내나 | 설정 |
|---|---|---|
| **A 기억 없음** | 아무 준비 없이 Claude Code를 쓰는 사람 (대부분) | 플러그인 끔. AI는 디스크의 프로젝트 파일은 뒤질 수 있다(실제 사용 그대로). 노트 사본·세션 기록·이 저장소는 못 읽게 막음 |
| **B 메모 폴더** | Obsidian 같은 md 폴더에 적어 두고 AI에게 "거기서 찾아"라고 하는 사람 | 같은 노트를 md 폴더로 두고, 작업 폴더 `CLAUDE.md`에 "지난 결정은 그 폴더에서 먼저 찾아라" 두 줄. AI가 Grep·Read로 직접 찾음 |
| **C 통째로** | 기억할 것을 전부 `CLAUDE.md`에 붙여 두는 사람 | 노트·실수 노트 63개 파일 전체(5.0만 자, 약 4만 토큰)를 작업 폴더 `CLAUDE.md`에 넣음. 모든 요청에 늘 들어감 |
| **D 세컨드 브레인** | 이 제품 | 플러그인 켬(찾기 방식 R 기본: 확실한 노트는 훅이 미리 넣고, 아니면 `brain find`) |

- 모델은 Haiku 5.5다(비용 때문). 토큰 수는 모델이 달라도 거의 같아서 Opus 5.5 값으로도 환산했다(턴 수는 모델마다 다를 수 있음 → 9절 한계).
- 허용 도구는 네 조건 모두 같다: `brain` 명령·스킬·Read·Grep·Glob. 그 밖의 명령(`lsof`, `ls` 등)은 거부된다. 실제 지식 폴더(`~/SecondBrain`)·이 저장소·`~/.claude`(세션 기록·메모리)는 모든 조건에서 읽기 금지로 막았다.
- **오염 검사**: 처음 실행에서 A가 디스크를 뒤지다 다른 조건용 노트 사본을 읽은 경우가 1번 나왔다. 그래서 조건마다 다른 조건의 자료와 시험 폴더 위쪽을 막고, 걸린 22번을 다시 쟀다(`bench/value/clean.py` 규칙: 다른 조건 자료 경로·시험 폴더 위쪽 전체 검색·A 답에 노트 id). 다시 잰 22번 중 5번은 또 위쪽을 검색하려 했지만 읽기 금지에 막혔고, 답에도 사본 내용이 없어 그대로 썼다.

- **붙으면 지킨다**: m2(Isolate.run)에서 D는 2번 모두 "최상위 함수로 빼고 단순 값만 (n_0038, L-0004)"을 계획에 넣었다. m3(회귀 시험 통과)에서는 "창이 좁아 ⌘+가 막힌 채 아무 일도 없이 통과한 것이 아닌지 본다"처럼 **실제로 겪은 실수의 구체적인 모양**까지 짚었다. 다만 이 두 상황은 일반 상식으로도 맞히기 쉬워 A도 3.5/4였다.
- **(고치기 전) 안 붙으면 안 쓴 사람과 같다**: 6개 중 4개 상황에서 훅이 실수 노트를 붙이지 못했다. 원인은 맞추기 규칙이다. 실수 노트의 상황 문장(trigger) 단어 머리가 요청에 절반 넘게 있어야 붙는다. 예: "실행 중인 프로세스(앱 등)를 끌 때" → [실행·중인·프로] 중 "포트 8080을 다른 앱 프로세스가 잡고 있어… 끄고 다시 켜 줘"에는 "프로" 하나만 있다(1/3). 그 결과 m4(그래프 흐림 막)에서 D는 1번 **"막을 InteractiveViewer 자식 Stack 안에"**라고 L-0007의 실수를 그대로 계획했다. A도 1번 같은 실수를 했다.
- **(고치기 전) C가 가장 잘 지켰다.** 실수 노트 7개가 늘 문맥에 있어서다. 대신 토큰이 D의 2.3배이고, 5절처럼 노트가 늘면 못 쓴다. → **실수 노트만은 C처럼 늘 보이게 하는 것**이 가장 싼 해법이다(8절 ①).
- **고친 뒤: 11/12, C보다 높다.** 실수 노트 목록이 세션 시작에 늘 들어가자, 말이 달라 훅이 못 붙이던 상황에서도 계획에 규칙이 들어갔다(2/8 → 7/8). 예:
  - m1(프로세스 끄기): "`ps -o lstart,command -p <PID>`로 시작 시각과 실행 주체를 확인하고, 직접 켠 것 같으면 끄기 전에 먼저 묻겠습니다" (2번 모두)
  - m4(흐림 막): "막을 `InteractiveViewer` 바깥 `Stack`에, 보이는 영역 기준으로… 축소·확대·가장자리 이동 상태에서 직접 확인" (2번 모두, 고치기 전에는 1번이 막을 안에 둠)
  - m6(화면 배율): "LayoutBuilder·크기 리스너와 되먹임이 없는지 먼저 확인… 그래프 화면에서 실제로 눌러 확인" (2번 모두, 고치기 전 0번)
  - 덜 지킨 것: m5(CSV 내보내기)는 "0건·많을 때·저장 실패 처리, 실제 앱에서 눌러 확인"까지 나왔지만 진행 표시가 빠져 0.5씩.
  - 토큰은 C의 0.47배(짝 비교 −41,615, 95% −62,659 ~ −20,996).
- **너무 많이 적용하지는 않았다**: 관계없는 요청 6번·지식 질문 36번의 답에 실수 노트를 끌어다 쓴 문장은 없었다(답에서 `L-00`·"지킬 규칙"을 찾아 확인).
- m5(L-0001: 오류 처리·진행 표시·실제 크기 데이터)는 C도 0.5/2였다. 계획 3줄로 묻는 형식이라 "실제 앱에서 눌러 확인"은 나와도 오류·진행 표시까지는 잘 안 나왔다.

| 노트가 이만큼이면 문맥(100만 토큰)이 참 | — | — | **약 1,530개** | 해당 없음 (1만 개 실측: `find` 43ms, 훅 67ms) |
| 그날 첫 세션(캐시 식음) 고정 문맥 쓰기, Opus | $0.064 | $0.066 | **$0.257** | $0.067 → 고친 뒤 $0.072 |

- 관계없는 요청에 D가 더 쓰는 것은 세션 시작 안내·스킬 목록이다(정밀 실측 596토큰, [토큰분석](토큰분석.md) 8절). 이번 6번의 중앙값은 +788토큰이다. 고친 뒤에는 실수 노트 7개 목록(940자)이 늘 들어가 +1,621토큰이다(토큰분석 9절).
- C는 질문 하나만 보면 싸다(4만 토큰이 캐시 읽기라 Opus로 약 $0.008). 하지만 **모든 요청·모든 턴에 4만 토큰이 따라다닌다**. 노트가 10배(500개)면 요청마다 약 32만 토큰이다. 그리고 노트 전체가 늘 AI에게 보인다(설계서 5.7, n_0022: 필요한 것만 보낸다).

## 6. 한 달로 환산하면 (가정을 밝힌 예시)

- **가정**: 개발자 1명, 한 달 22일. 하루 Claude Code 세션 8개, 요청 40개. 그중 **지난 결정·설정·해결법이 필요한 요청 5개**(월 110번), 나머지 35개는 관계없는 요청(월 770번). 지식 요청은 3절의 개인 결정 질문 실측값, 관계없는 요청은 5절 값을 쓴다. 모델은 Opus 5.5 API 값($4/$20, 캐시 쓰기 $5, 읽기 $0.20 / 100만 토큰).

| | A 기억 없음 | B 메모 폴더 | C 통째로 | D 고치기 전 | **D 고친 뒤** |
|---|---|---|---|---|---|
| 지난 지식 요청 110번 중 답을 얻음 | **9번** | 110번 | 110번 | 105번 | **110번** |
| 다시 설명해야 하는 요청 | 약 101번 (평균 526자씩) | 0 | 0 | 약 5번 | 0 |
| 월 입력 토큰 | 3,010만 | 3,140만 | **5,930만** | 2,620만 | **2,630만 (A보다 −13%)** |
| 월 비용 (캐시가 데워진 경우) | $13.83 | $15.37 | $15.79 | $10.69 | **$10.12** |
| 월 비용 (세션마다 캐시가 식는 경우) | $25.16 | $27.06 | **$60.99** | $22.57 | **$22.82** |

- **돈 차이는 크지 않다. 핵심은 "답을 얻느냐"다.** 같은 돈(오히려 조금 덜)으로 답 9개가 110개가 된다. 실수 노트 목록을 늘 넣어 관계없는 요청은 조금 늘었지만(+833토큰), 지식 요청의 턴이 줄어 월 토큰은 거의 그대로다.
- **구독(Pro·Max) 사용자에게는 토큰이 곧 사용 한도**다. 세컨드 브레인을 켜면 지식 요청에서 토큰이 줄어 한도가 더 오래 간다(월 −380만 토큰).
- 사람 시간은 쟀지 않았다. 다만 A에서는 "모른다"는 답 뒤에 사용자가 다시 찾아 설명해야 한다(월 약 101번). 이 시간이 토큰보다 크다.

## 7. 사용자에게 각인시킬 메시지 (숫자 근거와 함께)

홍보 페이지·발표에 그대로 쓸 수 있는 문장이다. 각 줄의 숫자는 이 문서의 실측이다.

| # | 메시지 | 근거 |
|---|---|---|
| 1 | **AI는 당신이 지난주에 정한 것을 모릅니다.** 물어본 24번 중 22번은 답을 못 했고, 그중 5번은 엉뚱한 답(다른 팀명, 다른 언어의 오류)이었습니다. | 3절 A |
| 2 | **세컨드 브레인을 켜면 24번 모두 답합니다.** 4번 중 3번은 찾는 과정 없이 바로(1턴), 중앙값 3.1초. | 3절 D 고친 뒤 |
| 3 | **모르는 AI가 오히려 더 비쌉니다.** 디스크를 뒤지느라 질문당 8.7만 토큰, 세컨드 브레인은 4.2만 토큰. 답 하나 얻는 데는 25배 차이입니다. | 3절 |
| 4 | **평소엔 거의 공짜입니다.** 관계없는 요청에는 +6%. 메모를 전부 CLAUDE.md에 넣으면 +151%입니다. | 5절 |
| 5 | **노트가 1만 개가 돼도 그대로입니다.** 찾기 43ms, AI에게 가는 양은 늘 5줄. CLAUDE.md에 넣는 방식은 약 1,500개에서 문맥이 찹니다. | 5절, 설계서 5.8 |

## 8. 이번에 찾은 약점과 고친 것

> 약점마다 고친 방법·시험 기록·지키는 자동 시험은 [기능검토](기능검토.md) 4절에 K-07(①)·K-08(②)·K-09(③)·K-10(④)·K-11(시험 오염)로 정리했다.

| # | 약점 | 근거 | 고칠 방법 (후보) → 결과 |
|---|---|---|---|
| ① | 실수 노트가 다른 말로 한 요청에 붙지 않음 (6개 상황 중 2개만 붙음) | 4절 | **(추천)** 세션 시작 안내에 실수 노트를 한 줄씩(상황 → 행동) 늘 넣는다. 지금 7개면 약 600토큰, 상한 30개면 약 2,500토큰. 세션마다 같아서 캐시를 다시 쓴다. C의 10.5/12에 가까워질 것으로 본다 / (보조) 맞추기를 trigger·action·diff 전체의 2글자 조각으로 넓히기 — 잘못 붙는 것이 늘 수 있어 회귀 시험 필요 / (보조) 실수 노트에 다른 말(별칭) 넣기 = 토큰분석 P7 → **추천안으로 고침 (설계서 v1.3.16)**: 7개 목록 940자, 지킴 6 → **11/12**, 안 붙던 상황 2 → 7/8. 대가는 세션마다 약 +833토큰 |
| ② | AI가 `brain` 명령을 파이프로 이음 (`brain find … \| head -50`, `;`) → 허용 목록 밖이라 거부되고 재시도로 턴이 늘거나 실패 | D 54번 중 12번(brain 호출 26번 중 16번), 실패 1번(k05) | `second-brain` 스킬에 "brain 명령은 `\|`·`;`·`&&` 없이 하나씩 부른다(출력은 이미 짧다)" 한 줄 → **고침**: 스킬과 세션 시작 찾기 줄에 넣음. 54번 중 0번(brain 호출 27번 모두 하나씩), 실패 0번 |
| ③ | 훅이 미리 넣는 노트(R2)가 엉뚱할 때가 있음 | "포트 8080… 다시 켜 줘"에 한반도감 재구축 노트(서버·다시가 겹침), "화면 배율 기능"에 `claude -p` 노트(앱·화면이 겹침) | 미리 넣기 기준(`isStrongMatch`)에 흔한 단어(서버·다시·앱·화면) 가중치를 낮추기. 지금은 데이터 경계 문장이 있어 해는 없고 토큰만 든다(약 100토큰) → **남음** |

- ①이 가장 중요했다. "같은 실수를 하지 않는다"는 이 제품의 두 번째 약속인데, 고치기 전에는 규칙 문장과 같은 말로 요청할 때만 지켜졌다. 고친 뒤 다시 잰 것은 세컨드 브레인 조건 54번(질문 18·실수 6·관계없는 3 × 2번)이다. 시험 질문은 고치기 전에 쓴 그대로이고, 고친 방법은 질문과 상관없이 모든 실수 노트를 보여 주는 것이라 이 질문에 맞춘 것이 아니다.

## 9. 한계

- **모델**: Haiku 5.5로 쟀다. Opus는 더 끈질기게 찾거나 더 빨리 포기할 수 있어 턴 수가 다를 수 있다. 토큰 환산은 같은 토큰 수를 Opus 값으로 곱한 것이다. Opus로 지식 질문 세트를 다시 돌리면 약 $5~10로 추정한다.
- **권한**: `dontAsk` 모드라 허용 목록 밖 명령은 거부됐다. 실제 사용에서는 사용자가 허락할 수 있다. 그러면 A는 더 많이 뒤지고(토큰↑), D의 파이프 실패는 "허락 요청"으로 바뀐다.
- **질문**: 질문은 이 사용자의 실제 노트에서 만들었다(개인 결정 12개). 다른 사용자·다른 분야에서 다시 재야 한다. 실수 상황 6개는 적다. 지킴 판정은 사람(나)이 계획을 읽고 매겼다(판정 표: `bench/value/judge_20261108.json`).
- **사람 시간**: "다시 설명하는 시간", "엉뚱한 답을 믿고 생긴 손해"는 재지 않았다. 다음에는 사람이 직접 같은 질문을 해 보며 시간을 잰다.
- **고친 뒤 측정**: 세컨드 브레인 조건만 다시 쟀다. A·B·C는 같은 날 앞서 잰 값이다. 실수 노트가 7개일 때의 결과이고, 30개 가까이 늘면 목록이 길어져 효과가 옅어질 수 있다 → 실수 노트가 늘면 같은 시험을 다시 돈다.
- **캐시**: 동시에 여러 개를 돌려 캐시 적중이 우연에 좌우됐다. 그래서 비용은 "고정 문맥은 데워짐/식음"으로 나눠 다시 계산했다(`summary.py`의 `cost_norm`). 토큰 수는 영향이 없다.
