# Fable 5.2 최적화·검증 작업 지시서 (11/14)

- **누가 읽나**: Claude Fable 5.2로 새로 연 Claude Code 세션. 사용자가 이 문서를 가리키며 "N번 작업 해 줘"라고 하면 그 절만 한다.
- **왜 Fable 5.2인가**: 1M 맥락으로 저장소를 한꺼번에 보고, 오래 걸리는 추론·에이전트 작업에 강하다. 이 프로젝트에서 11/11 독립 검토(K-17~K-38, S-1~S-9, O-1~O-9)로 이미 효과를 봤다. 대신 토큰 값이 Opus 5.5의 2배라 **판단·설계·감사**에만 쓰고, 반복 실행(실측)은 Haiku·Sonnet `claude -p`로 돌린다.
- **진행 순서**: 1 토큰 최적화 → 2 데이터 안전 감사 → 3 성능 → 4 보안 → 5 측정 방법 검증 → 6 설계서·코드 일치 → 7 지식 품질 감사 → 8 근거 기반 기능·스킬 추천. 한 세션에 한 작업. 끝나면 보고하고 멈춘다.
- **노력 수준**: 1·3·5·6은 high. 더 찾는 것이 중요한 2(데이터 안전)·4(보안)는 xhigh. max는 쓰지 않는다.
- **재사용 점검표 (모든 작업, 11/14 사용자 요청)**: 나중에 Fable 5.2 없이 다른 모델이 같은 효과를 내도록, 보고 끝에 이번에 쓴 방법을 프로젝트 이름 없이 따라 할 수 있는 점검표로 정리한다 — 판단 기준, 확인 순서, 빼면 안 되는 것(실패 사례), 전·후 숫자. 메인 세션이 세컨드 브레인 노트로 저장한다(1번 점검표는 n_0094).
- **비용 상한**: 실측은 큰 모델 한 번이 작은 모델의 약 30배다(1번에서 Opus 5.5 한 번 0.21~1.02달러). 상한을 넘기지 않게 돌고 있는 실행 몫까지 미리 잡는다(1번은 7달러 상한에 7.38달러).

  2. 판정에서 거꾸로 **기준**을 뽑는다: 들어올 때·확인할 때·쓸 때·시간이 지나면·모자란 곳(5.9 표)마다 구체적 규칙과 예.
  3. **기준 적용 전·후 비교표**(사용자 요청): 사본에 기준대로 후보를 처리한 "후" 판을 만들고, 지금("전")과 견준다 — 노트 수·종류별 개수, 보관·고침·합침 후보 수, 대표 사례 5개(전 내용 → 후 처리), 같은 질문 세트(`bench/questions.yaml` 30개 + 실제 사용 질문 몇 개)에서 찾기 정확도. 실제 AI로 답 정답률까지 재려면 비용을 먼저 묻는다.
  4. 노트 판정은 **후보**다. 실제 지식 폴더는 고치지 않는다. 사용자 판정(W1)과 견줄 수 있게 판정표를 남긴다.
- **보고**: 0절 보고 형식 + 판정표(id, 판정, 이유) + 기준 + 전·후 비교표 + 재사용 점검표(다른 모델이 주마다 같은 판정을 하려면 무엇을 보고 어떻게 판단하나).
- **끝난 기준**: 모든 노트에 판정이 있고, 기준이 단계별 규칙으로 정리되고, 전·후 비교표가 숫자로 있다.

## 8. 근거 기반 기능·스킬 추천 (읽기 전용, 11/14 추가)

- **목적**: 세컨드 브레인에 더할 기능·스킬을 아이디어가 아니라 **실제 사용 기록**에서 뽑는다. 7번 결과(지식 품질 문제, 빈 곳)를 근거로 쓰므로 7번 다음에 한다.
- **노력 수준**: high (읽을 것이 많고 서로 엮어 판단하는 일).
- **읽을 것**: `docs/신규버전_사용후기.md`, `docs/설계서_프롬프트이후.md`(특히 8.2 마감 뒤로 미룬 것, 5.9), `docs/교수님시스템_비교분석.md`(우리가 안 한 것), 7번 보고, 이 맥의 Claude Code 대화 기록(`~/.claude/projects/*/*.jsonl` — 사용자가 반복해서 시킨 일, 다시 물은 일, 막힌 곳. 읽기만, 양이 크면 먼저 크기와 예상 비용을 사용자께 묻는다), 지식 폴더(`brain topics`, `brain lint`).
- **할 일**: 기능·스킬 후보마다 — 근거(어느 기록·몇 번), 만드는 크기, 마감(12/08) 전 가능 여부, 발표 시연 가치, 스킬로 할지 앱 기능으로 할지, **넣지 말아야 할 이유(반론)**, Claude Code가 이미 하는 일과 겹치는지(L-0014: 공식 문서로 확인, 못 하면 "미확인"). 후보는 7±2개로 줄여 순위를 낸다.
- **반드시 평가할 사용자 아이디어 3가지 (11/14)**:
  1. **작업에 맞는 모델 추천(+ 다른 모델 지휘)** — 자동 전환이 아니라 **추천까지**(사용자 11/14). 세컨드 브레인이 "이 작업은 지난번 Sonnet으로 충분했고 얼마 들었다" 같은 우리가 잰 결과를 쌓고, 큰 작업을 시작할 때 훅·스킬이 그 지식을 꺼내 추천하는 방식. Claude Code가 이미 하는 것(하위 에이전트 모델 지정, 지휘)과 겹치는 곳, 훅이 모델을 바꿀 수 있는지(공식 문서로 확인)를 따진다.
  2. **모델별 최적 프롬프트(적은 토큰·빠름·높은 품질)** — 공식 안내에서 얻는 일반 원칙(싸다)과 우리 작업으로 잰 검증된 최적(비싸고 판이 바뀌면 낡음)을 나눠, 무엇을 지식으로 쌓을지와 낡음 관리(5.9)를 함께 설계한다. 근거: 11/14 토큰 실측에서 같은 지시문의 효과가 Haiku −20%·Opus −5%로 모델마다 달랐다.
  3. **저장 잊음 해결 (11/14)** — 자동 저장은 세션 시작 안내의 문장 한 줄뿐이라 긴 작업(하위 에이전트, 압축)에서 잊힌다(사용 후기 11/13). 질문마다 독촉하는 알림은 억지 지식을 만들 위험으로 빼기로 했다. 후보: 세션이 끝난 뒤 새 맥락에서 따로 뽑기(앱 자동 정리, 비용), 압축 직전 훅이 남긴 "저장 안 한 지식" 목록을 실제 저장으로 잇기, 큰 작업을 마칠 때만 한 번 확인하기. 이 맥의 실제 대화 기록에서 "저장했어야 했는데 안 한 곳"을 세어 어느 방법이 맞는지 근거로 고른다. 저장보다 꺼내기(요청 훅의 단어 일치 한계)도 함께 본다.
- **시작 전에 알 것 (11/14, 7번 뒤 사용자 지적 두 가지)**:
  1. **7번 판정 하나가 틀렸다** — n_0060을 "교훈은 L-0006·L-0012에 있다"며 보관 후보로 봤지만, 그 두 규칙은 일반 원칙이라 이 노트의 구체 버그가 없었다. 또 메인 세션이 n_0060·n_0054 요약을 날짜·상태 말("지난 일")로 바꾸자고 했다가 사용자가 "다른 프로젝트에서 같은 버그를 찾으면 이 요약을 보고 꺼내 쓰겠냐"고 바로잡았다. AI는 제목·요약만 보고 노트를 열지 정하므로 요약에는 문제·해결(찾을 말)을 남긴다. → 실수 노트 L-0019(승인 대기), 점검표 n_0095에 두 줄 추가, 실제 지식 폴더에서 제목·요약이 틀린 8개를 고쳤다(사용자 승인, n_0060은 보관 대신 제목·요약을 다시 씀). 지식 품질 쪽 후보를 낼 때 이 기준을 따른다.
  2. **저장 잊음이 또 일어났다** — 위 교정을 받고도 메인 세션(Opus 5.5)이 검증 에이전트에 넘기지 않았고, 사용자가 "실수 노트는 알아서 쓰는 것 맞냐"고 물은 뒤에야 넘겼다. 자동 저장(지식)뿐 아니라 **교정 → 실수 노트** 경로도 세션 시작 안내 문장만으로는 잊힌다. 위 3번(저장 잊음 해결)에 이 경로를 넣어 평가한다 — 사용자가 AI 답을 고친 순간을 무엇으로 알아챌지, 대화 기록에서 "교정이 있었는데 실수 노트가 안 생긴 곳"이 몇 번인지.
- **보고**: 0절 보고 형식 + 후보표 + 재사용 점검표(근거로 기능을 고르는 방법).
- **끝난 기준**: 후보마다 근거와 반론이 있고, 마감 전에 할 것 1~3개를 권장안으로 고른다.
