# 세컨드 브레인 토큰 분석 (2026-11-07)

- **질문**: 세컨드 브레인을 쓸 때 토큰이 얼마나 드나, 어떻게 검증하고 어떻게 줄이나 (사용자 요청 11/07)
- **방법**: 같은 프롬프트로 `claude -p`(Haiku)를 조건별로 돌려 응답의 `usage`를 비교했다(실측). 실제 지식 폴더 대신 사본, 사용자 설정 대신 시험용 설정을 썼다. 측정 비용 합계 약 $0.09.
- **도구**: 실측 `bench/token/live.py`, 예산 시험 `packages/brain_cli/test/token_budget_test.dart`

## TL;DR

> 세컨드 브레인을 켜 두면 세션마다 **952토큰**(Claude Code 기본 맥락 약 2.7만의 3.5%)이 더 든다. 관계없는 요청에는 **0토큰**이다.
> 가장 큰 낭비는 크기가 아니라 **캐시**다. 세션 시작 안내에 세션 id가 들어가 세션마다 내용이 달라진다. 그래서 Claude Code가 지난 세션의 캐시를 못 쓰고 **약 1.35만 토큰을 새로 캐시에 쓴다**. 세션 시작 비용이 약 9배가 된다.
> ① 세션 id 빼기·② 세션 시작 안내 줄이기는 **8절에 적용** (677 → 321토큰, 세션 시작 비용 약 1/9).
> **추천 vs 추천+깃허브(7절, 실제 Claude Code 30번)**: 추천(R)이 지금보다 입력 토큰 −31%·턴 2.9→2.0·정답 8→9/10. 깃허브 아이디어를 더한 RG는 R과 차이 없음(질문 30개 × 2번 짝 비교: 입력 +3.0%, 95% 구간이 0을 포함) — 턴을 없애는 것이 가장 크고 둘 다 이미 그것을 한다. **R 확정**.
> **찾기 방식 비교(6절)**: 출력을 줄이면 AI가 노트를 한 번 더 열어 오히려 토큰이 늘었다(평균 7.4만 → 9.3만). 토큰은 출력 글자보다 **턴 수**가 좌우한다. 추천은 R1(약한 후보를 보여 주지 않음, 신뢰성) + R2(확실한 노트를 훅이 미리 넣어 찾기 턴을 없앰).

## 2. 실측 결과 (claude -p, Haiku, "안녕")

| 조건 | 입력 토큰 합계 | 캐시 쓰기 | 캐시 읽기 | 비용 |

| 자동 저장 안내만 켬 (세션 id 포함) | 27,488 (+342) | **13,498 (매번)** | 13,988 | **$0.0029** |

- 같은 조건을 3번 돌려 숫자가 같았다. 첫 실행은 캐시가 비어 있어 모두 비싸다.
- **캐시가 깨지는 원인**: 지식 요약은 세션마다 같아서 두 번째부터 전부 캐시에서 읽는다. 자동 저장 안내에는 `세션 id는 <id>`가 들어가 세션마다 글자가 다르다. 그래서 그 뒤의 약 1.35만 토큰을 매번 캐시에 다시 쓴다. 비용은 모델 가격에 비례하므로 Opus에서는 차이가 더 크다.
- **지식 찾기** (같은 사본, "내 세컨드 브레인에서 아이폰 사진 백업 방법 찾아서 짧게 알려 줘"): `brain find` 한 번, 대화 2턴, 입력 64,591토큰(대부분 캐시 읽기), $0.0052. 노트를 열지 않고 find 5줄만으로 답했다.
- **프로젝트 결정을 묻는 질문** ("한글 검색은 어떤 방식으로 하기로 했었지?"): 플러그인을 켜도 `brain find`를 쓰지 않았다. 메모리에 있는 저장소 문서 위치를 보고 `Grep`으로 설계서를 찾았고, 3턴·124,652토큰이 들었다. 답은 맞았다. 이 질문의 정답은 설계서에 있고, 세컨드 브레인 노트(n_0012)는 그 요약이다.

## 6. 비교분석: 신뢰성을 지키면서 토큰을 줄이는 찾기 방식 (2026-11-07)

교수님이 직접 만든 시스템은 문서를 찾는 데 약 10토큰이 든다고 하셨다(사용자 회상, 측정 방법은 모름, [피드백기록](주간보고/피드백기록.md)). 우리 방식을 여러 형식으로 바꿔 신뢰성과 토큰을 쟀다.

### 6.1 출력 형식만 비교 (돈 안 듦, `packages/brain_core/tool/retrieval_formats.dart`)

실제 지식 폴더 노트 40개, 검색 시험 질문 20개(답 있음)와 답 없는 질문 6개.

| 형식 | 정답이 보임 | 답 없는 질문에 "없음" | 평균 출력 (≈토큰) |
|---|---|---|---|
| A 지금: 5줄, 제목+요약+폴더 | 95% | 0/6 | 436 |
| B 1줄, 제목+요약+폴더 | 70% | 0/6 | 93 |
| C 3줄, id+제목 | 90% | 0/6 | 95 |
| D 5줄, id+제목 | 95% | 0/6 | 157 |
| E 엄격 검색(모든 조각 일치)만 | 15% | 6/6 | 13 |
| F 훅 미리 넣기 (단어 머리 2개 이상, 최대 3) | 65% | 5/6 | 30 |
| H 5줄 id+제목 + 약한 후보 (약) 표시 (`brain find --brief`) | 95% | **6/6** | 182 |

- 출력만 보면 H가 답 신뢰성(95%)을 지키면서 글자는 58% 줄이고, 답 없는 질문도 모두 알아챘다.

### 6.2 실제 Claude Code로 비교 (`claude -p` Haiku, 질문 10개 × 2, 비용 약 $0.10)

질문 8개(답 있음)와 2개(답 없음). "근거 노트 id를 적어라"로 정답 여부를 판정했다.

| 조건 | 정답 | 평균 입력 토큰 | 평균 턴 | 질문당 비용 |
|---|---|---|---|---|
| A 지금 (요약 포함) | 8/10 | **74,249** | **2.7** | $0.0050 |
| H 짧게 (id+제목, 약한 후보 표시) | 9/10 | 93,237 | 3.2 | $0.0053 |

- **출력을 줄였더니 오히려 토큰이 늘었다.** 요약이 없으니 AI가 거의 매번 `brain show`로 노트를 한 번 더 열었다(턴 +1). A에서는 3건이 find 요약만으로 2턴 만에 답했다.
- **토큰을 가장 많이 쓰는 것은 출력 글자가 아니라 턴 수다.** 턴이 하나 늘 때마다 맥락 약 3만 토큰을 다시 읽는다(캐시 읽기라 값은 10%지만 토큰 수에는 그대로 잡힌다). find 출력 300자를 아끼는 것보다 턴 하나를 줄이는 것이 약 100배 크다.
- 정답 차이(A의 X 1건)는 AI가 brain을 아예 안 쓰고 답한 경우였다(1턴). 형식 차이가 아니다.
- 답 없는 질문 "주식 배당 투자 전략"은 A·H 둘 다 관계없는 노트(n_0009 타이쿤 게임)를 근거로 적었다. H는 (약) 표시를 붙였지만 AI가 무시했다. **약한 후보는 표시만으로는 부족하고, 아예 보여 주지 않거나 "없음"이라고 분명히 말해야 한다.**

공통점은 **처음에는 작게 보여 주고, 필요한 것만 더 연다**(점진적 공개)는 것이다. 우리 find→show가 이미 이 구조다. 이번 실측에서 덧붙일 교훈은 하나다. 단계를 늘리면 턴이 늘어 오히려 비싸다. **첫 단계에서 답이 될 만큼은 보여 줘야 한다.**

### 6.4 결론과 추천 (신뢰성 우선, 그다음 토큰)

| 순서 | 방안 | 신뢰성 | 토큰 | 근거 |
|---|---|---|---|---|
| **R1** | find는 요약을 유지하고(A), 약한 후보는 **보여 주지 않고 "확실한 노트 없음"**으로 끝낸다 | 답 없는 질문 0/6 → 6/6 (출력 비교), 엉뚱한 근거 인용을 막음 | 같거나 줄어듦 | 6.1 H, 6.2 주식 사례 |
| **R2** | 질문형 요청에도 훅이 **확실히 맞는 노트 1~3개를 id·제목·요약 한 줄로 미리 넣는다** (지금은 만들기 요청만) | 미리 넣은 것의 1등 정답 12/13 | 맞으면 find 턴 1개를 아낌(약 3만 토큰), 틀리면 약 30~60토큰 | 6.1 F |
| R3 | 노트를 열 때는 섹션 단위(`#섹션`)와 1,500자 한도를 쓴다 | 같음 | 긴 노트에서 줄어듦 | serena·context7 |
| R4 | 5절 P1(세션 id 빼기 → 캐시) | 같음 | 세션 시작 비용 약 1/9 | 2절 |
| 버림 | 출력을 id+제목으로 줄이기(`--brief`를 기본으로) | 같음 | **늘어남** (턴 +0.5) | 6.2 |

- **"문서 찾기 10토큰"과 비교하면**: 우리 찾기 명령은 10~20토큰으로 같다. 결과까지 세면 R2가 맞을 때 AI가 찾기 명령을 쓰지 않으므로 **찾는 데 0턴·약 30~60토큰**이다. 교수님 자료를 받으면 같은 방법(6.2)으로 재서 비교한다.
- `brain find --brief`는 실험용으로 남겨 둔다(기본 아님). 목록을 많이 훑을 때만 쓴다.

## 7. 추천(R) vs 추천 + 깃허브에서 배운 것(RG) 실측 비교 (2026-11-07)

세 방식을 `BRAIN_RETRIEVAL` 환경변수로 바꿔 가며 같은 질문 10개(답 있음 8, 답 없음 2)를 실제 Claude Code(Haiku)로 돌렸다. 질문은 "세컨드 브레인에서 찾아"라는 말 없이 평소처럼 묻고 "근거 노트 id를 적어라"만 붙였다. 비용 합계 약 $0.14.

| 방식 | 무엇을 하나 |
|---|---|
| base (지금) | find 5줄(제목+요약), 훅은 만들기 요청에만 관련 노트 |
| **R** (추천) | R1: find에서 질문 단어가 본문까지 2개 이상 안 맞는 노트는 숨김, 없으면 "확실한 노트 없음". R2: 질문과 확실히 맞는 노트(제목·요약에 단어 2개 이상)를 훅이 id·제목·요약 한 줄로 미리 넣음 |
| **RG** (추천 + 깃허브) | R + aider식 글자 예산(600자 안에 순위대로, 위 2개만 요약) + serena·context7식 "질문에 맞는 본문 한 줄"(↳) + claude-mem식 "열면 본문 몇 자" 표시 |

| 방식 | 정답 (답 있음 / 답 없음) | 평균 입력 토큰 | 평균 턴 | 1턴에 끝난 질문 | 10개 비용 |
|---|---|---|---|---|---|
| base | 8/10 (7/8, 1/2) | 84,450 | 2.9 | 1 | $0.052 |
| **R** | **9/10 (7/8, 2/2)** | **57,988 (−31%)** | **2.0** | 3 | **$0.044 (−15%)** |
| RG | 9/10 (7/8, 2/2) | 58,682 (−31%) | 2.0 | 4 | $0.044 (−15%) |

- **R이 base보다 확실히 낫다.** 훅이 미리 넣은 노트로 바로 답하거나 `brain show` 한 번으로 끝나 찾기 턴이 줄었다(평균 2.9 → 2.0턴). 답 없는 질문에서 엉뚱한 노트를 근거로 쓰던 것도 없어졌다(주식 배당: base는 n_0009 인용, R은 "없음").
- **RG는 R과 거의 같다** (토큰 +1.2%, 비용 같음). "본문 한 줄" 덕에 1턴에 끝난 질문이 3 → 4개로 늘었지만, 다른 질문 하나는 오히려 한 턴 더 썼다. 질문 10개로는 차이를 가릴 수 없는 수준이다.
- **왜 차이가 작나**: 토큰을 가장 많이 줄이는 것은 턴을 없애는 것(R2)이고, R과 RG 둘 다 이미 그것을 한다. 깃허브에서 가져온 것들(글자 예산, 필요한 줄만, 크기 표시)은 결과 글자를 다듬는 쪽이라 턴 하나(약 3만 토큰)에 비하면 작다.
- **둘 다 못 푼 것**: "띄어쓰기 상관없이 한글 찾기"는 세 방식 모두 AI가 brain을 쓰지 않고 답했다(1턴, 오답). 질문 단어(띄어쓰기·찾기)와 노트 제목(한글 검색 색인·2글자 분할)이 달라 훅도 미리 넣지 못했다. 이것은 형식이 아니라 **다른 표현을 잇는 문제**다(5절 P7과 같은 뿌리).
- **한계**: 질문 10개·한 번씩·Haiku. R과 RG의 차이(±1%)는 이 표본에서 우연과 구별되지 않는다. 확정하려면 질문 30개 × 2번(약 $0.3)으로 다시 잰다.

**결론**: R(추천)을 적용한다. RG의 "질문에 맞는 본문 한 줄"은 1턴 답을 늘리는 효과가 보여 큰 표본에서 다시 재 볼 가치가 있다. 글자 예산·크기 표시는 지금 규모(노트 40개)에선 효과가 안 보여 넣지 않는다.

### 7.1 질문 30개 × 2번으로 다시 (R vs RG, 2026-11-07)

질문 30개(검색 시험 20개 + 답 없는 질문 10개)를 R·RG로 두 번씩, 모두 120번 돌렸다(Haiku, 비용 $0.54). 같은 질문·같은 차례끼리 짝지어 비교했다.

| 방식 | 정답 (답 있음 / 답 없음) | 평균 입력 토큰 | 평균 턴 | 1턴에 끝남 | 60번 비용 |
|---|---|---|---|---|---|
| **R** | 56/60 (36/40, 20/20) | **59,041** | 2.10 | **20** | **$0.268** |
| RG | 57/60 (37/40, 20/20) | 60,828 (+3.0%) | 2.12 | 16 | $0.275 (+2.6%) |

- **짝 비교**: RG − R 입력 토큰 평균 +1,786, 95% 구간 −2,536 ~ +6,158 (부트스트랩 5,000번). 0이 구간 안에 있어 **차이가 있다고 말할 수 없다**. 같은 질문을 두 번 돌려도 입력이 평균 3,400~6,600토큰씩 흔들린다.
- 정답도 56 vs 57로 1개 차이(우연 범위). RG는 1턴에 끝난 질문이 오히려 4번 적었다.
- **결론 확정: R을 쓴다.** 깃허브에서 가져온 글자 예산·필요한 줄만·크기 표시는 지금 규모에서 토큰도 신뢰성도 바꾸지 못했다. 가장 큰 효과(턴 없애기 R2, 약한 후보 숨김 R1)는 R에 이미 있다.
- **틀린 것** (두 방식 공통 원인): "띄어쓰기 상관없이 한글 찾기"는 질문이 아니라 명령으로 읽혀 4번 모두 실패 → 검색 시험 질문 문장을 "띄어쓰기 상관없이 한글을 찾는 방식은?"으로 고칠 것. R은 "스위프트 빌드"에서 정답(n_0004)을 약한 후보로 숨긴 적 1번(R1의 대가), RG는 원래 검색 시험에서 놓치던 "엑스코드" 1번.
- **판정 주의**: 처음 자동 판정은 답 없는 질문에서 "없어. 나온 것은 n_0032(관계없음)"처럼 **없다고 말하면서 찾아본 노트 id를 적은 것**까지 틀림으로 셌다(9/20). 답 문장을 다시 읽어 "없다고 했는가"로 고쳤다(20/20). 다음 측정부터 판정 기준을 미리 정해 둔다.
- 지금 방식(base)은 이번 30개로는 다시 재지 않았다. 10개 측정에서 R보다 입력 +46%·턴 +0.9였다(7절 표).
