# 세컨드 브레인 사용기 (개발하며 직접 써 본 피드백)

- **목적**: 개발하는 AI(Claude Code)가 실제로 `brain` 명령으로 지식을 찾고 저장하면서 느낀 불편·장점을 적는다. 사용자 입장의 문제를 일찍 찾기 위해서다.
- **쓰는 법**: 날짜, 상황, 무엇이 불편/좋았나, 원인, 조치(고침·과제)를 한 항목에 적는다. 고친 것은 `(고침)`을 붙인다.

## 핵심 목표로 본 경험: "AI가 실수하지 않고, 내 지식을 작은 토큰으로 쏙쏙"

세컨드 브레인의 목표는 두 가지다. ① AI가 같은 실수를 되풀이하지 않는다 ② AI가 내 지식에서 필요한 것만 적은 토큰으로 가져온다. 개발하는 AI(Claude Code)로서 실제로 겪은 것을 숫자와 함께 적는다.

### 작은 토큰으로 가져오기 (2026-11-07 실측, 노트 29개)

| 방법 | 글자 수 | 비고 |
|---|---|---|
| 노트 29개를 통째로 넣기 | 23,634자 | 노트 1만 개면 약 800만 자 — 넣을 수 없다 |
| `brain find 검증 에이전트` (5줄) | 285자 | 제목·요약·폴더만 |
| `brain show n_0020` (노트 하나) | 696자 | 출처 줄·데이터 경계·연결 줄 포함 |
| find + show 한 번 | 약 1,000자 | 통째의 **약 4%**. 노트가 늘어도 거의 그대로 |
| 세션 시작 온보딩 요약(`_profile.md`) | 231자 | 주요 주제 5개 + 자주 받은 교정 |
| 관계없는 요청의 훅 | **0자** | 맞는 규칙이 없으면 아무것도 넣지 않는다 |
| 규칙이 맞을 때 훅 | 224자 (규칙 1개) | 최대 3줄 |

- **좋았던 점**: 개발 중에 "NFC", "검증 에이전트"를 찾을 때 5줄만 보고 열지 말지 정할 수 있었다. 요약 줄 60자가 핵심이다(#1에서 40자로 잘리던 것을 고친 뒤 노트를 다시 여는 일이 줄었다).
- **아쉬운 점**: 표기가 다르면 0줄이다("엑스코드" → Xcode 노트를 못 찾음, 29자 "찾은 노트 없음"). 이미 저장된 노트에 별칭이 없어서다(#5). 노트가 많아지면 별칭 제안이 꼭 필요하다.

### 실수하지 않기: 실제로 일어난 일

1. **실수가 규칙이 되기까지 (11/06)**: 사용자가 "기본적인 건 지키면서 해"라고 교정했다(정리 시작이 멈춘 것처럼 보인 일). 실수 노트 L-0001(기능 만들 때 → 오류 처리·진행 표시·실데이터 시험)로 저장했고, 사용자가 배운 것 화면에서 승인했다.
2. **규칙이 다음 요청에 들어감 (11/07)**: 사용자가 기능 수정을 요청하자 훅이 L-0001을 자동으로 대화에 넣었다. 그 덕에 이번 작업(할 일 AI 추천)에 동의 창·진행 표시·멈추기·오류 문구를 시키지 않아도 처음부터 넣었다. 세컨드 브레인이 의도대로 동작한 첫 사례다.
3. **AI가 스스로 알아챈 실수 (11/07)**: "앱 켜 줘"에서 실행 중인 앱을 시험 잔재로 넘겨짚고 꺼 버렸는데, 1분 전에 사용자가 켠 앱이었다. 이 사례를 `brain-verifier` 에이전트에 넘겼더니 ① 교정이 맞음 ② 일반 규칙이 됨 ③ 기존 규칙과 안 겹침 ④ 회귀 시험 T-0001과 충돌 없음을 확인하고 L-0003(프로세스를 끌 때 → 시작 시각·실행 주체 확인)을 **승인 대기**로, 사례를 회귀 시험 T-0002로 저장했다. 약 30초. 자동 감지라 승인 대기로 둔 판단도 설계대로다.
4. **헛걸림 (11/07)**: 백그라운드 작업 완료 알림이 들어올 때도 훅이 L-0001·L-0002를 넣었다. 알림 문구 속 단어에 규칙의 단어 머리가 맞았기 때문이다. 사용자 요청이 아닌데 토큰을 쓴 셈이다 → 과제: 시스템 알림 모양의 입력(`<task-notification>` 등)은 훅에서 건너뛰기.
