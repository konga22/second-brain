# 찾기 고민 — AI가 "일하는 방식" 노트를 못 꺼내는 문제

11/14 기록. 다음 주(11/19 2주차 보고 전후)에 이어서 이야기하려고 문제·지금까지 한 것·남은 판단을 한곳에 모은다. 구현 내용은 [설계서_프롬프트이후](설계서_프롬프트이후.md) 5.10 끝(작업 방식 노트 훅)·5.11(목차 먼저 보여 주기)에 있다.

## TL;DR

- 응모 세션에서 "분석하고 설계해줘"라고 했는데, AI가 세컨드 브레인의 초반 설계 방식 노트(n_0086)를 꺼내 쓰지 않았다.
- 원인은 검색 단어 문제만이 아니다. **요청은 "무엇을 만들지"를 말하고, 노트는 "어떻게 진행하는지"를 말한다.** AI는 검색이든 목차든 주제가 같은 노트만 고른다.
- 지금까지 장치 두 개를 만들었다: ① 만들기·설계 요청이면 `작업방식` 태그 노트를 훅이 직접 붙인다(커밋 `e0aefaa`) ② 목차를 먼저 보여 준다(Fable 세션, 커밋 `cc056c2`, 11/14 합치고 설치).
- 실패 당시 조건(태그 없음) 재현: 기존 0/6, 목차만 0/4, **목차 + "일하는 방식 노트도 고른다" 문장 6/6**. 태그가 있는 지금 상태에서는 기존 판도 2/2. 표본이 작다(칸마다 2~4번).
- **해결 상태 (11/14 밤, 설치한 판 기준)**: "찾아서 근거로 대는 것"은 해결(시험 조건 안). "노트대로 진행하는 것"은 확인 못 함 — 8절. 자세한 것은 7절.

## 1. 무슨 일이 있었나

- 응모·대회 프로젝트 세션에서 사용자가 응모 자동화를 "분석하고 설계해줘"라고 했다.
- 사용자는 예전에 "초반 계획을 어떻게 짰는지"를 세컨드 브레인에 저장해 두었다(n_0086).
- AI는 만들 대상의 주제어(브라우저 자동화, 헤드리스 에이전트, 크롤링)로만 3번 찾았고 n_0086을 쓰지 않았다. 사용자가 "세컨드 브레인에 있다"고 알려 준 뒤에도 AI가 고른 검색어 3개 중 2개는 빈손이었다.
- 지적을 받은 뒤 실수 노트 L-0029(설계 요청이면 진행 방식도 따로 찾는다)가 생겼다. 하지만 문장 규칙만으로는 지켜지지 않은 적이 많아서(L-0013) 장치로 받치기로 했다.

## 2. 원인 세 가지

| 원인 | 설명 |
|---|---|
| AI가 주제어로만 찾음 | AI는 "응모 자동화와 같은 주제"를 찾는다. "이 사용자가 일하는 순서"는 찾을 대상으로 떠올리지 않는다 |
| 요청 훅이 단어 2개 이상 겹쳐야 붙임 | 요청과 노트(제목·요약·태그)에 같은 단어가 2개 이상 있어야 노트를 붙인다. 요청 "응모 … 설계해줘"와 노트 "초반 설계 순서"는 거의 안 겹친다 |
| "설계해줘"가 만들기 요청으로 안 잡히고, "해줘"를 못 뗌 | 만들기 의도 단어에 설계·계획·기획이 없었다(고침). 검색에서 조사는 떼지만 "해줘·하자·했어" 같은 요청 어미는 못 떼서 "설계해줘"로는 "설계"가 든 노트를 못 찾는다(안 고침) |

## 3. 지금 검색이 단어를 맞추는 방식 (설명했던 것)

- 글자를 2글자 조각으로 나눠 맞춘다(SQLite FTS5). 뜻이 아니라 **글자**가 같아야 걸린다.
- 제목 칸(제목 + 별칭 + 태그)은 3배, 본문 칸(요약 + 본문)은 1배로 친다.
- 요청의 단어를 **전부** 쓴다: 먼저 "모든 단어가 있는 노트"(엄격), 모자라면 "하나라도 있는 노트"(느슨)로 채운다. 단어 하나로만 찾는 것이 아니다.
- 단어 끝 조사("웹훅이" → "웹훅")는 떼지만 요청 어미("설계해줘")는 못 뗀다.
  - 실제: `설계해줘` → 찾은 노트 없음, `초반 설계해줘` → n_0086("초반" 덕분), `분석하고 설계해줘` → 관계없는 역설계 도구 노트.
- 교수님 프롬프트에는 검색 엔진·색인이 없다. AI가 `index.md`(목차) → 섹션 목차 → 페이지를 읽고, 모자라면 `rg -il <키워드>`로 찾는다. 키워드는 AI가 고르고, 요청마다 노트를 붙여 주는 장치는 없다.

## 4. 사용자가 낸 생각과 지금 판단

| 생각 | 지금 판단 |
|---|---|
| 키워드 + 의도로 찾자 ("초반 설계해줘" → "초반" + "설계") | 맞는 방향이고 원래 그렇게 만든 구조다. "해줘"를 못 떼는 것이 막는다 |
| 변하는 말(해줘·해라·아니·안돼)을 떼고 변하지 않는 말(초반·설계)만 남기자 | 할 수 있다. 떼는 목록을 두 개로 나눈다(통째로 빼는 대화어 / 단어 끝 요청 어미). 단점: 단어가 하나뿐인 요청은 흔한 노트가 섞인다("설계" → 역설계). 원래 형태도 함께 찾으므로 지금 찾히던 노트가 사라지지는 않는다. 형태소 분석기는 정확하지만 마감 전에는 크다. **아직 안 함 — 질문 세트 전후 비교 뒤 결정** |
| 검색엔진처럼 노트 뒤에 키워드·태그를 붙여 두자 | 별칭(aliases) 칸이 이미 있고 제목과 같은 3배로 친다. 찾을 때 쓸 말을 별칭에 채우는 일은 후보로만 있다. 다만 사용자가 무엇을 원하는지에 따라 맞는 노트가 달라서, 태그만으로 "의도"를 맞추지는 못한다 |
| AI가 직접 찾는 방식(교수님 방식)이 제일 좋아 보이는데 왜 안 되나 | AI가 세컨드 브레인에 무엇이 있는지 모르고 검색어를 짐작한다(세션 시작 때 주제 이름만 받음). 일에 집중하면 찾기를 건너뛴다(평소 말투 요청에서 찾기 스킬 읽음 0/24, 훅이 넣은 노트를 연 비율 13%). → 목차를 먼저 보여 주자고 해서 ②를 만듦 |

## 5. 만든 장치와 결과

### ① 작업 방식 노트를 훅이 붙임 (11/14, 커밋 `e0aefaa`, 실제 앱에 적용)

- 만들기 의도 단어에 설계·계획·기획 요청을 더함: 걸릴 말 7/7, 헛걸림 0/5.
- 만들기·설계 요청이면 `작업방식` 태그가 붙은 노트를 **단어와 상관없이** 붙인다(최대 2개).
- 실제 폴더에서 응모 세션의 두 요청 모두 n_0086이 붙는 것을 확인. 실제 AI가 그 노트를 쓰는지는 아래 "지금 상태" 실험에서 본다.
- 약점: **태그가 있어야 붙는다.** 저장 스킬에 "방식 노트에는 `작업방식` 태그" 한 줄을 넣었지만 문장 안내라 빠뜨릴 수 있다.

### ② 목차 먼저 보여 주기 (Fable 세션, 커밋 `cc056c2`, 11/14 합치고 설치)

- 만들기·설계 요청이면 세션의 첫 요청에 노트 제목 목차를 붙인다(지금 94개, 약 3,900자). `brain toc` 명령, 찾기가 빈손이면 목차를 보라고 알림.
- 돈 안 드는 측정: 찾기 30문 96.7% 그대로, 만들기 요청이 아닌 요청 1,020개의 훅 글은 기존과 같음, 지난 요청 1,113개에서 훅 글 합계 약 16.6만 → 33.6만 자.
- **응모 재현(유료, Opus, 실패 당시 조건 = 태그 붙이기 전)**:

  | | n_0086을 연 횟수 | 하는 모습 |
  |---|---|---|
  | 기존 판 | 0/4 | 맨손으로 평균 2.2번 검색 |
  | 새 판(목차) | 0/4 | 목차에서 주제가 가까운 노트를 4번 모두 골라 씀. 일하는 방식 노트는 제목만 보고 고르지 않음 |

- 진행 중(11/14 밤): "지금 상태"(태그 + 훅이 있는 상태) Opus 4번, 목차 안내 글을 보강한 판("설계·계획을 어떤 순서로 진행했는지 적은 노트는 다른 프로젝트 것이어도 고른다") Opus 4번. 상한 18달러.
  - **지금 상태 (끝, 4번)**: 기존 판 2/2, 새 판 2/2 — 둘 다 초반 설계 방식 노트를 근거로 대고 그 순서를 따랐다. ①(태그 + 훅)이 듣는 것이다. 검색 횟수는 새 판 0번, 기존 2~3번. 표본이 작다(판마다 2번).
  - **안내 글 보강판 (끝)**: 그때 상태에서 Opus 4/4, Fable 5.2 2/2 — 모두 n_0086을 열고 근거로 댔고 검색은 0번. 같은 조건의 기존 판은 Fable도 0/2. 값은 Opus 입력 토큰 +8%, 실행 하나 +0.09달러.
  - 합계: 본 실행 21번, 15.81달러(상한 18달러 안). 자세한 표는 설계서_프롬프트이후 5.11.
  - **한계 (Fable 보고)**: 칸마다 2~4번. 보강 문장은 실패를 본 뒤 쓴 것이라 이 시나리오에 맞춰졌을 수 있다 — 방식 노트가 아닌 노트로는 안 쟀다. "그 방식대로 진행하는가"는 못 가렸다(21번 모두 설계 문서를 바로 쓰고 끝에 "정해 주실 것"을 붙임 — 화면 없는 실행의 기본 행동). 태그만 빼고 L-0029 문장을 남긴 조건에서는 기존 판도 1/1로 찾았다(짧은 세션에서는 규칙 문장도 듣는다).

## 6. 지금까지의 생각 (11/14, 메인 세션)

- 목차만 붙인 첫 판은 0/4였다. 목차는 고를 후보를 넓힐 뿐, AI가 무엇을 중요하게 보는지는 바꾸지 못했다.
- **목차 + "일하는 방식 노트도 고른다" 한 문장**은 태그가 없어도 6/6(Opus 4, Fable 2)으로 찾았다. 목차가 있어야 그 문장이 들을 자리가 생긴다(목록에서 알아보기). 그래서 ②는 ①을 받치는 장치로 쓸모가 있다 — 태그를 잊은 방식 노트도 잡는다. 처음에 "목차가 더 근본적"이라고 한 말은 목차만으로는 틀렸고, 목차 + 문장으로는 맞았다.
- ①(태그 + 훅)은 지금 상태에서 기존 판도 2/2로 듣는다. 이번 문제의 주 해결은 ①이고, ②는 태그 잊음 대비와 검색 횟수 감소(2.5 → 0)다.
- 조심할 것: 보강 문장은 이 실패에 맞춰 쓴 것이라 다른 종류의 노트에서도 듣는지 모른다. 실제 긴 세션에서 지켜지는지는 설치 뒤 기록으로 봐야 한다(L-0013).

## 7. 해결 방식과 해결 상태 (11/14 밤, 설치한 판 기준)

### 해결 방식

1. **방식 노트는 훅이 직접 붙인다 (주 해결)**: 노트에 `작업방식` 태그를 달고, 만들기·설계 요청이면 단어가 안 겹쳐도 훅이 그 노트를 "사용자가 정한 작업 방식"으로 붙인다. AI가 찾을지 말지에 기대지 않는다.
2. **목차와 고를 종류를 함께 보여 준다 (받침)**: 만들기·설계 요청이면 세션 첫 요청에 노트 제목 목차를 붙이고, "설계·계획·개발을 어떤 순서로 진행했는지 적은 노트는 다른 프로젝트 것이어도 고른다"를 안내에 넣는다. 태그를 잊은 방식 노트도 AI가 목록에서 알아본다.
3. **만들기 의도 단어를 넓혔다**: "설계해줘·계획 짜 줘·기획해 줘"도 만들기 요청으로 본다(걸릴 말 7/7, 헛걸림 0/5).
4. 정리: 검색어를 고쳐서 푸는 문제가 아니었다. 요청(무엇을 만들지)과 노트(어떻게 진행하는지)의 글자가 안 겹치므로, **붙여 주거나 목록에서 고르게** 했다.

### 해결된 것 (확인함)

| 무엇을 | 근거 |
|---|---|
| 응모 세션과 같은 말에 방식 노트가 붙는다 | 설치한 훅에 같은 요청을 넣어 봄: 목차(노트 94개)·안내·n_0086이 함께 붙음(4,433자) |
| 태그가 있으면 AI가 그 노트를 근거로 댄다 | 지금 상태 재현 2/2(기존 판도 2/2) |
| 태그를 잊어도 목차 + 안내로 찾는다 | 그때 상태 재현 6/6(Opus 4, Fable 2), 목차 없는 기존 판은 0/6 |
| 다른 요청은 그대로다 | 만들기 아닌 요청 1,024개의 훅 글이 기존과 글자 하나까지 같음, 찾기 30문 96.7% 그대로 |

### 아직 해결 안 됨 / 확인 못 함

| 무엇을 | 왜 남았나 | 어떻게 확인·해결할지 |
|---|---|---|
| **노트대로 진행하는가** (큰 결정을 먼저 묻고 시안부터) | 실험 21번 모두, 노트를 본 실행도 못 본 실행도 설계 문서를 바로 쓰고 끝에 "정해 주실 것"을 붙임 — 근거로 대는 것까지만 달라짐 | 8절 1번에서 재는 방법을 정한다 |
| 실제 긴 세션에서 지켜지는가 | 실험은 두 마디짜리 짧은 세션. 긴 작업에서는 안내가 잘 안 지켜진 적이 많다(L-0013) | 설치한 판으로 쓴 실제 세션 기록에서 확인 |
| 만들기 단어에 안 걸리는 설계급 요청 | 표본 판정에서 설계급 요청의 절반가량을 놓침. 단어를 넓혀도 붙는 세션 수는 안 늘어 그대로 둠 | 그때는 `brain find` 빈손 안내만 받친다. 실제 기록에서 놓친 사례가 나오면 다시 본다 |
| 하위 에이전트 | 훅 글을 못 받는다 | 범위 밖, 후보로 둠 |
| 방식 노트가 아닌 노트 | 안내 문장이 이번 실패에 맞춰 쓴 것이라 다른 종류에도 듣는지 모름 | 8절 2번 |

## 8. 다음 주에 이야기할 것

1. **"그 방식대로 진행하는가"를 어떻게 잴지.** 이번 실험은 노트를 근거로 대는지까지만 가렸다. 실제 세션 기록에서 진행 순서(아이디어 → 큰 결정은 사용자가 → 시안 먼저)를 따랐는지 보는 방법을 정한다.
2. **목차 판(②)을 계속 쓸지(11/14 합치고 설치함 — 되돌리려면 이전 방식 스위치 `toc`).** 얻는 것: 태그 없는 방식 노트도 6/6, 검색 0번. 드는 것: 훅 글 약 2배(지난 요청 기준 16.6만 → 33.6만 자), 실행 하나 입력 토큰 +8%. 다른 종류 노트로 한 번 더 잴지도 함께 정한다.
3. **태그를 잊는 위험을 어떻게 막을지.** 보기: 저장할 때 "진행 순서·방법" 같은 말이 있으면 태그를 권하는 알림(상태 문장 알림과 같은 방식) / 목차 안내 보강 / 그대로 둠.
4. **요청 어미 떼기를 할지.** 질문 세트(찾기 30문·평소 말투 14문·바뀐 지식 12문)와 말투 시험으로 전후를 재고, 맞는 비율이 안 내려가면 넣는다.
5. **별칭 채우기를 할지.** 노트마다 찾을 때 쓸 말을 별칭에 넣는 일. 누가(저장 스킬·정리 기능) 언제 채울지.
6. **교수님께 물을지.** "AI가 사용자의 일하는 방식을 스스로 찾지 않는다"는 문제는 교수님 방식(AI가 목차를 읽고 고름)에서도 같다. 2주차 보고 "문제와 대응"·"확인 요청 사항"에 넣을지 정한다.
