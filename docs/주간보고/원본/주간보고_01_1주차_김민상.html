01요약

한눈에 보기
진척
1주차 목표(개발 환경, 빈 앱, Supabase 연결, FTS5 확인)를 11/06에 마쳤고, 2~4주차 범위의 핵심 기능까지 앞당겨 구현했다. 설계서는 v1.3 → v1.3.28
되는 것
macOS 앱 화면 전체, brain CLI, Claude Code 연동(스킬 4개·훅·검증 에이전트), 대화 중 자동 저장, 실수 노트와 회귀 시험, 홍보 페이지 첫 배포
실측
"지난번에 정한 ○○가 뭐였지?" 같은 질문 24번을 실제 Claude Code에 물었다. 세컨드 브레인이 없으면 맞게 답한 것이 2번(나머지는 "기록이 없다" 17번, 틀린 답 5번), 켜면 24번 모두 맞게 답했다. 질문당 입력 토큰은 8.7만 → 4.2만
독립 검토(11/11)
만든 세션과 다른 AI 모델로 코드·문서 전체를 다시 읽어 새 약점 23개와 서버 약점 9개를 찾았다. 가장 급한 3개(명령 자동 허락 훅의 보안 문제, 앱에 옛 CLI가 묶이던 문제, 그래프 꼬임)는 같은 날 고쳤다. 앱은 응용 프로그램 폴더에 설치해 검색으로 켤 수 있게 했다
남은 큰 일
검토에서 찾은 약점(높음 7개), 서버(AI 게이트웨이) 배포 전 수정과 앱 안 AI 질문 시험, AI 크레딧 차감, 설치 파일(.dmg), Codex 연동
용어
경로 A / 경로 B
A는 사용자가 쓰는 AI(Claude Code)가 기기 안에서 brain 명령으로 지식을 바로 찾는 길(우리 서버 안 거침), B는 앱 안에서 질문해 우리 서버(AI 게이트웨이)를 거치는 길
실수 노트 / 회귀 시험
사용자가 AI 답을 고쳐 준 것을 규칙으로 남긴 노트와, 그 규칙이 과거 교정 사례와 부딪히지 않는지 다시 돌려 보는 시험
노트
지식 하나를 적은 md 파일(마크다운, 글자만 든 문서 파일) 하나. 사용자 맥의 지식 폴더(~/SecondBrain)에 주제별 폴더로 저장된다. "노트 1만 개"는 이런 파일 1만 개라는 뜻이다
검색 정확도 (recall@5, "리콜 앳 파이브")
미리 정답을 정해 둔 질문으로 검색했을 때, 정답 노트가 검색 결과 위 5개 안에 든 질문의 비율. 예: 질문 30개 중 29개면 96.7%
독립 검토
코드를 만든 AI와 다른 모델에게 영역별(저장·보안·CLI·서버·앱·문서·성능)로 처음부터 다시 읽게 하고, 찾은 약점 가운데 심각한 것은 임시 폴더에서 직접 재현해 확인하는 방식

3.1 실측 결과

항목결과방법
지난 결정을 묻는 질문 24번 (예: "리포트 팀명이 뭐였지?")맞게 답한 횟수: 세컨드 브레인 없이 2번("기록 없음" 17번, 틀린 답 5번) → 켜면 24번. 맞는 답 하나당 토큰 105만 → 4.2만과거 대화에서만 정한 내용 12개를 2번씩, 새 대화에서 물음
같은 실수 상황 6가지 × 2번안 쓰면 4.5/12, 세컨드 브레인 11/12 (고치기 전 6/12)실수 노트를 세션 시작에 늘 보이게 고친 뒤
관계없는 요청의 추가 토큰세컨드 브레인 +6%, 메모를 CLAUDE.md에 통째로 넣으면 +151%같은 노트로 4조건 비교
검색 정확도 (평소 말투 질문 30개)정답 노트가 검색 결과 위 5개 안에 든 질문 26개 → 29개 (86.7% → 96.7%, recall@5). 정답이 1등인 질문 24개한영 표기 사전, 묻는 말 빼기
노트가 1만 개일 때 속도 (md 파일 1만 개)찾기(brain find) 173 → 43ms(목표 50), 처음 색인 226 → 30초, 그래프 첫 표시 0.78초(목표 1초)시험용으로 자동 생성한 md 파일 1만 개(본문 300~1,500자)로 측정
주입 시험공격 노트를 넣고 16번 중 따른 것 0번실제 Claude Code
세션마다 드는 토큰약 1,600토큰 (기본 맥락의 약 6%, 실수 노트 7개일 때). 지금 15개라 안내가 2,615자로 늘었고 토큰은 다시 잴 예정실측
그래프 꼬임 (노트 76개, 직접 연결 47개)직접 연결끼리 겹침 43번 → 0번, 다른 주제에 섞인 노트 22 → 4실제 지식 폴더, 고치기 전후 비교
명령 자동 허락 훅허락하면 안 되는 명령 32개 중 허락한 것 27개 → 0개고치기 전에 시험을 먼저 씀
자동 시험코어 67개, CLI 13개, 화면 통합 시험 통과11/11 다시 실행

비교 시험은 개발자 본인의 노트와 질문으로, Haiku 모델로 잰 것이라 다른 사용자·모델에서 같은 숫자가 나온다는 뜻은 아니다. 검색 96.7%는 놓친 질문을 보고 고친 뒤 같은 질문으로 잰 값이다. 측정 스크립트와 질문 세트는 저장소 bench/에 있다.

3.2 직접 써 본 기록 (사용기)

이 프로젝트를 개발하는 동안 개발에 쓰는 AI(Claude Code)에 세컨드 브레인을 연동해 두고, 지식을 찾고 저장하면서 불편했던 점과 잘 된 점을 그때마다 적었다(11/06 ~ 11/08, 49건). 설계만으로는 보이지 않던 문제를 사용자 입장에서 일찍 찾기 위해서다. 3.1의 숫자 대부분은 이 기록에서 나온 문제를 고치고 다시 잰 결과다. 대표 사례는 아래와 같다.

#써 보니원인조치·배운 점
3평소 말투로 물으면 노트를 15%만 찾음 ("웹훅이 실패하면?"이 "웹훅을 다시 보낸다"를 못 찾음)검색어의 조사·어미까지 그대로 찾음조사·어미 떼기 → 95%
12실수 노트를 승인한 뒤 첫 요청에서, 시키지 않은 진행 표시·멈추기·오류 문구가 처음부터 들어감훅이 맞는 규칙을 대화에 자동으로 넣음의도대로 동작한 첫 사례
19전날 의심만 하고 넘어간 오류가 다음 날 그대로 다시 남의심한 내용을 지식으로 남기지 않아 다시 알려 줄 수 없었음확정된 결정·해결은 대화 중에 자동 저장하도록 변경
28"고쳤고 시험도 통과"라고 보고한 떨림이 그대로였음시험 창이 좁아 고치려는 동작이 시험에서 일어나지 않음(빈 통과)시험이 그 동작을 실제로 일으켰는지 먼저 확인하는 규칙
30세컨드 브레인을 켜면 세션 시작 비용이 약 9배안내 글에 세션마다 다른 값이 있어 캐시를 못 씀안내를 세션마다 같은 세 줄로 → 시작 비용 약 1/9
34찾기 결과를 줄였더니 토큰이 오히려 늘어남 (7.4만 → 9.3만)요약이 없어 AI가 노트를 한 번 더 열었고, 턴마다 맥락을 다시 읽음토큰은 출력 글자보다 턴 수가 좌우 → 첫 결과에 답이 될 만큼 보여 줌
49규칙과 다른 말로 시키면 실수 노트가 안 붙음 (같은 실수 상황 6/12)규칙 문장의 단어가 요청에 있어야 붙는 방식세션 시작 때 규칙 목록을 늘 보여 줌 → 11/12

전체 기록은 저장소 docs/세컨드브레인_사용기.md에 있다. 개발 중에 받은 교정은 실수 노트 15개로 남아 지금 개발 세션에 적용되고 있다.
